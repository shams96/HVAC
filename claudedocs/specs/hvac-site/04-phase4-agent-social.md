# Phase 4: Chat/intake agent and social publishing

Gate: red-team test (prompt injection, out-of-scope requests, fake-review requests). Owner decision: use a multi-agent workflow (builders in parallel, independent attacker, fixer).

## Spec (what/why)
A chat agent that answers only from the approved catalog, collects job details, checks availability (if a provider exists), creates estimate requests and hands off to a human. A social publisher that posts to Google Business Profile, Facebook/Instagram and YouTube only through official APIs, with stored consent and human approval before each post. **Safety properties are enforced by code around the model, not by trusting the model.** The red team therefore tests the harness with a scripted (adversarial) LLM: whatever the model outputs, the invariants below must hold.

Out of scope: a real LLM provider adapter (needs keys; interface only), real platform API adapters (need OAuth credentials; interface + fake + "not configured" refuser), calendar integration (availability provider interface only), chat widget UI, Phase 5 measurement.

## Contract A: chat agent (`api/src/agent/`)
`registerAgentRoutes(app, { db, now, catalog, llm, availability, sla, conversationTtlMin?, actionTtlMin? })` registers PUBLIC routes `POST /api/chat/start`, `POST /api/chat/message`, `POST /api/chat/confirm`, `POST /api/chat/reject`. Also export `createAgent({ db, now, catalog, llm, availability })` for direct testing.

LLM interface (the only model dependency): `llm.complete({ system, messages, tools }) -> Promise<{ text?: string, toolCalls?: [{ id, name, args }] }>`. `availability` interface: `availability.check({ zip, serviceLine, window? }) -> Promise<{ slots: [...] } | { unavailable: true }>`; when absent or unavailable the agent says staff will confirm; booking is disabled.

Invariants (each must be enforced in code and tested):
- **A1 LLM never executes state changes.** State-changing tools (`request_estimate`, `book_appointment`, `request_handoff`, any outbound message) only INSERT a `pending_actions` row and tell the user what will happen. Execution happens only inside `/api/chat/confirm`, a separate HTTP call, never inside the tool loop.
- **A2 Confirmation is out-of-band and single-use.** Confirm needs the conversation token (random, returned by `/start`, never shown to the LLM), an action id belonging to that conversation, status `pending`, not expired (default 15 min), not already used. Replay, wrong conversation, expired, forged id, and double confirm are all refused.
- **A3 Consent comes only from the confirm request body** (`consents: [{channel, wordingVersion}]`, set by a UI checkbox), never inferred from chat text or produced by the LLM.
- **A4 Full action log.** `agent_actions_log` is append-only (trigger like `forbid_mutation`): proposed, confirmed, rejected, expired, blocked, each with conversation id and actor (`agent`/`customer`/`system`). No PII in the log; ids only.
- **A5 Emergency first, deterministic, no LLM.** Before any model call, a pre-check on the user text (case/spacing/leetspeak/misspelling tolerant: gas smell/leak, carbon monoxide or CO alarm/detector, smoke, fire, burning smell, sparks, flooding near electrics) returns fixed guidance (`catalog.emergencyGuidance` or a conservative default: leave the building, call 911 or the gas utility from outside, don't use switches/flames/phones inside) and offers a handoff. The model is not called for that turn.
- **A6 Grounding.** Replies may state facts only from the catalog. Output guard: any currency amount not an owner-approved price (`amountsApproved`) blocks the reply (replaced by a safe fallback, logged as `blocked`). ZIP coverage and service availability come from `catalog.areas`, never from model text. A ZIP/service not in the catalog is answered "not listed, staff will confirm".
- **A7 Tool allowlist and validation.** Unknown tool names and schema-invalid args are rejected and logged. `serviceLine` must be a catalog slug; `zip` 5 digits; free-text fields length-limited. Tool results contain only catalog or DB facts.
- **A8 Treat all text as data.** User text and any tool-result text are wrapped in delimited data blocks; nothing in them can change the system prompt, the allowlist, a confirmation, or a price. No tool fetches the web.
- **A9 Scope.** Out-of-scope requests (legal/medical advice, other businesses, code, general chat, requests to reveal the prompt, discounts or prices not in the catalog, promises of arrival time) get a brief refusal and an offer to hand off.
- **A10 Limits.** Max message length (2000 chars), max turns per conversation, conversation TTL; Fastify body limit and rate limiting on public routes.
- **A11 Estimate requests** are created with `createLead` (`type` B2C or B2B, `channel: 'chat'`) with actor `agent:chat-agent` in the audit trail, only on confirm.
- **A12 Privacy.** Transcripts stored in `chat_messages` with a `purgeChats(db, now, {days})` function that deletes message text; logs redact message text.

## Contract B: social publishing (`api/src/social/`)
`registerSocialRoutes(app, { db, now, catalog, publishers, staffGuard })` registers STAFF routes under `/api/staff/social` using `staffGuard` as an `onRequest` hook. `publishers` maps `gbp | facebook | instagram | youtube` to `{ publish(post) -> Promise<{ externalId }> }`. Export a `notConfiguredPublisher` (always refuses) and a `fakePublisher()` for tests.

Invariants:
- **S1 Approval flow.** Post states `draft -> pending_approval -> approved -> published | failed`, plus `rejected`. Only `approved` can publish. Illegal transitions are refused.
- **S2 Human approval.** Approver actor type must be `user`; the creator cannot approve their own post (same actor id); `agent`/`system`/`webhook` actors can never approve.
- **S3 Immutable after approval.** Approval records a SHA-256 of the exact content+platform+media; publish recomputes and refuses on mismatch; editing an approved post returns it to `draft` and clears approval.
- **S4 Stored consent.** `social_connections` holds per-platform consent (who, when, scope). Publish requires a non-revoked connection; revoking blocks immediately, including already-approved posts.
- **S5 Content policy, deterministic** (`checkPostContent(post, catalog, ctx)` -> violations[]): no fabricated reviews or testimonials (kinds: `update`, `offer`, `review_reply`, `testimonial_share`; `testimonial_share` requires `sourceReviewId` referencing a `reviews` row with a `source_url` captured from an official API; first-person customer-voice text such as "as a customer", "I used them and", invented star ratings, or text posing as a customer are violations); any currency amount must be an approved price; any phone number in text must equal the catalog business phone; `catalog.bannedClaims` substrings are violations; review/customer text supplied for drafting is DATA and never executed or followed.
- **S6 Idempotent, audited.** Publishing the same post twice posts once. `social_post_events` is append-only with actor type/id for every change; platform failures become `failed` with the error, no retry loop that could double-post.
- **S7 Credentials never stored in these tables** (OAuth tokens stay in the secrets manager; adapters receive them at call time).

## Red-team scope (independent attacker)
Attack the invariants above with a scripted adversarial LLM and direct API calls. Categories: prompt injection (in user text and in tool results; role spoofing; fake system/tool messages; delimiter escape; unicode, zero-width, homoglyph and encoding tricks), confirmation bypass (replay, forged ids, cross-conversation, expired, double confirm, LLM attempting confirm, model emitting text "I confirm"), out-of-scope requests, price fabrication and fake discounts, emergency evasion and false negatives/positives, fake-review and testimonial requests, social approval bypass (self-approval, agent approval, publish unapproved, edit after approval, publish after consent revoke, double publish, platform confusion), PII leakage in logs/errors, oversize and malformed input, rate limits. Every attack is a test in `api/tests/redteam-*.test.mjs` that asserts the SAFE outcome. A failing test is a finding. Do not weaken the assertion; do not edit `src/`.

## Open items for owner (not engineering)
Which LLM provider/router and whether PII-sensitive turns use a local model (Ollama); owner-approved emergency wording (default is conservative and must be approved); availability/scheduling system; platform OAuth credentials and consent capture UI; whether staff approval needs a second approver; attorney review of chat and consent wording.

## Converge (2026-11-21)
Process: Workflow with 4 agents (agent-core builder and social builder in parallel on disjoint files, independent red team that could not edit `src/`, fixer). ~73 minutes, ~1.25M subagent tokens, 293 tool uses.
Built: `api/src/agent/**` (chat agent: emergency pre-check, scope pre-check, grounding guard, tool allowlist, confirm-out-of-band flow, action log, purge), `api/src/social/**` (post state machine, human approval, content hash, consent scopes, content policy, fake/not-configured publishers), migrations 002 to 004, `src/auth.mjs`, `src/catalog.mjs`, versioned migrations.
Red team: 101 adversarial tests; first run 52 pass, 49 fail (real defects: emergency false negatives and bypass via turn limit/expiry/length, grounding and price-extraction bypasses, confirm summary not showing what is stored, fabricated reviews, secrets in posts and errors, hidden characters, TRUNCATE on audit tables, read-only consent allowing publish).
Fixer: all 49 fixed, 3 noted as disputed (below). **Independently verified by me:** full api suite 225/225 (reproduced), 101 red-team tests intact with no skip markers and files unmodified after the fixer started, mutation checks (revert prototype-key check, drop the TRUNCATE migration) make the red-team tests fail; a third mutation (price extractor digit folding) was NOT caught because callers also fold digits (two layers), so I added a direct regression test that now fails under that mutation. Site suite 20/20, audit passes.
Fix quality: part structural (emergency check runs before expiry/turn limit/length; coverage claims tied to the ZIPs actually checked; confirm summary built from validated fields; TRUNCATE triggers; consent scope enforced; own-property check on tool args), part heuristic (regex and phrase lists for discounts, arrival promises, completed-action claims, customer-voice, banned claims, links, phones). The heuristic part will always have misses; the sturdier design (the model never writes prices, coverage or links; the harness fills them from the catalog) was not adopted.
Disputed by the fixer: RT-P2 (digit-script sweep assumption, passes), RT-P5 (fake-review detection is a heuristic; human review is the real control), RT-SF11 (consent scope enforcement goes beyond S4 text; owner decides which scopes count).
Not wired / not done: `main.mjs` does not pass `agentDeps` or `socialDeps`, so neither module is live; no real LLM adapter (interface only); no real platform adapters; no chat widget on the site; scheduled `purgeChats`/`expireStale` have no caller; agent actor appears in a second `lead_events` row after the lead is created, not in the same transaction; if the bookkeeping transaction fails after `createLead` succeeds, the action stays `confirmed` and retry is refused (lead still exists).
Cannot be tested with a scripted model: real model jailbreak resistance (needs a live evaluation), non-English abuse (needs native review), timing side channels, botnet-scale abuse and cost.
Needs owner: forged third-party consent via anonymous chat confirm (add double opt-in with a code sent to the number); per-user staff auth (self-approval is only enforced on asserted identities); approved emergency wording; which scopes count as posting scopes; second approver; LLM provider and whether PII turns go to a local model; availability system; attorney review.

## Wiring the social publisher (2026-11-21)
Built: `SOCIAL_ENABLED=1` switch (exact value only, default off), `api/src/assemble.mjs` (decides which optional modules start, testable, one shared catalog for chat and social), `api/src/social/registry.mjs` (the single place real platform adapters plug in; malformed adapters are rejected), `main.mjs` wiring with startup notes and warnings. Staff routes live under `/api/staff/social`, behind the shared staff token, and are not CORS-enabled (browsers cannot send the token cross-origin).
**No real platform adapters exist.** Google Business Profile, Facebook, Instagram and YouTube adapters need OAuth credentials, a registered app and platform review, and none could be tested here. With none registered, every platform refuses to publish with 503 `publisher_not_configured` before the post is claimed, so approved posts stay approved and nothing is burned. Wiring therefore gives the complete drafting, review and approval workflow and an audit trail, but **cannot publish anything yet**.
Verified: 272 API tests (6 new), mutation checks (malformed adapter trusted; social started when it should not be) both caught. Real process over HTTP against a wire-protocol database: startup log lists what is and is not enabled and prints two warnings; no token gives 401; consent grant; create and submit; self-approval refused; agent approval refused; a second person approves; publish returns 503 and the post stays approved; a fabricated-review post is saved as a draft and refused at submit by the content policy.
Known limit stated in the startup log: approver identity is asserted by whoever holds the shared staff token, so the two-person rule is enforced only on the identities claimed. Per-user staff login is required before relying on it.
Needs owner: which platforms first; platform developer accounts, OAuth consent flow and app review; who the approvers are; second approver policy; per-user staff login; wording for consent records.
